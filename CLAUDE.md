This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Next.js 13 (Pages Router) frontend for a referendum/polling platform. It talks to a separate NestJS backend
(sibling repo `../my-first-nest-app`) over a generated OpenAPI client. Georgian-language codebase and
comments are the norm — match that style in new code/comments unless told otherwise.

## Commands

```bash
yarn dev              # dev server + API-client watcher (concurrently runs `next dev` and `watch:api`)
yarn dev:next          # dev server only, no API-client watcher
yarn dev:test          # dev server with ENVIRONMENT=Test
yarn dev:preprod       # dev server with ENVIRONMENT=Preprod
yarn dev:prod          # dev server with ENVIRONMENT=Production

yarn build:prod        # production build (ENVIRONMENT=Production)
yarn start             # start built app

yarn lint              # next lint

yarn test              # jest
yarn test:watch        # jest --watch
npx jest path/to/file.test.ts               # single test file
npx jest -t "test name substring"           # single test by name

yarn generate:api       # regenerate API_Client/client from ../my-first-nest-app/swagger.json
yarn analyze             # bundle analyzer build (ANALYZE=true)
```

No CI lint/test gate config was found beyond `.gitlab-ci.yml`; check it before assuming a step is unnecessary.

## Architecture

### API client is generated, not hand-written
`API_Client/client/` is fully generated by `scripts/generate-api.js` from the backend's `swagger.json`
(read from `../my-first-nest-app/swagger.json`, a sibling directory — the backend must be running/built
first so it emits that file). **Never hand-edit files under `API_Client/client/`** — regenerate with
`yarn generate:api` instead, or edits will be silently lost. `API_Client/index.ts` is the hand-written
layer on top: it builds one axios instance per API group (`AuthAPI`, `QuestionAPI`, `AnswerAPI`,
`UserAnswerAPI`, `CategoriesAPI`, `FavoritesAPI`, `UserAPI`, `StatsAPI`), each taking
`(acceptLanguage, accessToken)` and wiring auth headers + timeout/size limits + error interceptors.
Server-side calls get keep-alive http/https agents (gated on `SSR` from `constants.ts`); client-side
calls don't.

### Auth
NextAuth (`pages/api/auth/[...nextauth].ts`) with three providers: `CredentialsProvider` (calls the
NestJS backend's `/auth/login` directly via axios) and OAuth via Google/Facebook (whose `signIn` callback
posts the profile to backend `/auth/google` or `/auth/facebook` to mint a backend session). JWT session
strategy; `access_token`, `role`, and `id` from the backend are threaded through the `jwt` → `session`
callbacks and end up on `session.accessToken` / `session.user.role` / `session.user.id`. Role-based access
for the admin dashboard is centralized in `hooks/useAdminGuard.ts` (`isAdmin`, `isDenied`, `isLoading`) —
reuse it rather than re-deriving role checks in pages/layouts. The nextauth handler also patches
`res.status` to turn 401→200 on `callback/credentials`, working around a Next dev-server bug that would
otherwise show the internal `_error` page instead of returning NextAuth's normal error payload.

### i18n and routing
`next-translate` + `next-translate-routes` drive locale-prefixed routing for `ka`/`en`/`ru` (plus an
internal `default` locale). `middleware.ts` redirects the `default` locale to `ka` for normal pages, while
explicitly passing through `/api/*`, `/_next/*`, and static files unmodified — this exists because
next-translate-routes' rewrites + a Next.js matcher together break API routes (a documented bug), so this
middleware deliberately has no `matcher` export and instead filters via conditionals inside the function
body. Be careful changing this — reintroducing a `matcher` config is what previously broke API auth
callbacks. Translation strings live under `locales/{en,ka,ru}`.

### Environments
Four app environments — `Dev`/`Test`/`Preprod`/`Production` — selected via the `ENVIRONMENT` env var at
build/dev time and exposed to the client as `NEXT_PUBLIC_ENV` (see `next.config.js` `env` block).
`constants.ts` derives `IS_DEV`/`IS_TEST`/`IS_PREPROD`/`IS_PROD`/`SSR` flags from that, plus the backend
`API_URL`/`AUTH_URL`/`BASEPATH`/`CDN_URL` read from `NEXT_PUBLIC_*` env vars. See `.env.example` for the
full list of required env vars (OAuth client IDs/secrets, NextAuth secret, analytics IDs, etc.).

### Component layout
- `components/pages/<feature>/` — one folder per page/feature (e.g. `dashboard`, `askQuestion`,
  `questionDetail`, `profile`), each typically with `index.tsx`, `style.ts` (styled-components), and
  sometimes `schemas.ts` (yup/zod validation) and colocated `*.test.tsx`/`*.test.ts`.
- `components/shared/` — cross-page building blocks (Header, Footer, AuthModal, QuestionCard, Pagination…).
- `components/ui/` — atomic/design-system-level components (Button, TextInput, Radio, Alert, Icon…).
- `pages/` — Next.js route files; these stay thin and delegate to `components/pages/<feature>`.
- `theme.ts` — typed styled-components theme (see `styled.d.ts` for the module augmentation).

### Path alias
`@/*` maps to the repo root (`tsconfig.json` and `jest.config.js` both define it) — e.g.
`@/constants`, `@/API_Client`, `@/components/ui/Button`.

### Testing
Jest + `next/jest` + Testing Library, jsdom environment. Tests are colocated with source
(`*.test.ts(x)` next to the file under test, e.g. `components/pages/dashboard/schemas.test.ts`), not in a
separate `__tests__` tree.
